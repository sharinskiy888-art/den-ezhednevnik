## 3. Все обращения к облаку
Адрес облака: `https://axpglqvvevwttpnmuvam.supabase.co`. Каждый запрос несёт публичный ключ `apikey`; после входа ещё `Authorization: Bearer <токен>`. Токен обновляется сам за минуту до истечения; при 401 — одна повторная попытка, потом «Войдите снова».

### Вход (`/auth/v1`)
| № | Функция `sync.js` | Метод и адрес | Отправляет | Получает |
|---|---|---|---|---|
| 1 | `signUp` | POST `/auth/v1/signup?redirect_to=…` | email, пароль | пользователь (+ токены, если без подтверждения письмом) |
| 2 | `signIn` | POST `/auth/v1/token?grant_type=password` | email, пароль | `access_token`, `refresh_token`, `expires_at`, `user{id,email}` |
| 3 | `refresh` | POST `/auth/v1/token?grant_type=refresh_token` | `refresh_token` | новые токены |
| 4 | `resetPassword` | POST `/auth/v1/recover?redirect_to=reset.html` | email | письмо с кодом и ссылкой |
| 5 | `verifyRecoveryCode` | POST `/auth/v1/verify` | email, код, `type:recovery` | токены |
| 6 | `consumeRecoveryFromUrl` | GET `/auth/v1/user` | токен из ссылки подтверждения регистрации (для ссылки восстановления запроса нет, токен просто сохраняется) | пользователь |
| 7 | `updatePassword` | PUT `/auth/v1/user` | новый пароль | пользователь |
| 8 | `signOut` | POST `/auth/v1/logout` | — | — |

Особенность: `getSession()` смотрит, каким облаком выдан токен (поле `iss`). Если другим — забывает вход и просит войти заново (так прошёл переезд 13.10). Этим же механизмом удобно переключаться на новый сервер.

## 5. Какие поля есть в данных (из `app.js`)
- **Задача** (неизвестные поля сохраняются как есть, поэтому сервер хранит данные как непрозрачный JSON): `id, title, date (ГГГГ-ММ-ДД), time, priority (low/normal/high), note, completed, autoCarry, carryCount, carriedFrom, repeat, recurrenceSource, reminder, reminderUtc, notified, subtasks[{title, done, doneBy, doneAt}], proofNote, photo, attachment{name, type, data, size}, photoCapturedAt, updatedAt`.
- **Надгробие:** `{id, __deleted: true, updatedAt}`.
- **Операция финансов:** `id, kind (expense/income), title, amount, category, photo, occurredAt, updatedAt`. Сумма — просто **число** до 2 знаков после запятой, валюта не хранится (в английском интерфейсе та же цифра показана в $), не копейки. Лимиты — целые.
- **Состояние приложения** (метка `__type: 'app_state'`): `profile{name, photo}`, `periodPlans[{id, text, scope, plannedDate, anchorDate, period (у старых), createdAt}]`, `financeLimits{категория: сумма}`, `updatedAt`.
- **Поручение (payload):** поля задачи **без** личных `autoCarry, priority, repeat, reminder, reminderUtc, notified`, но **с** `photo` и `attachment` (base64, документ до 4 МБ) и `completed`; плюс `status (new/accepted/open/question/review/completed)`, `statusBy, statusAt, subtasks[].doneBy/doneAt, reports[{id, by, at, text, photo?, voice?, voiceSec?}] (последние 50), activity[{type, email, at, status?}] (последние 30), nudgeAt, nudgeNumber, inviteReminderAt, inviteReminderNumber`.
- **Только на устройстве, в облако не уходят:** PIN (хэш от `<id пользователя>:<pin>`), настройки напоминаний (копия уходит в `push_subscriptions`), тема, язык.
- Все данные на устройстве хранятся под id пользователя (`…:<user id>`). **Значит, на новом сервере у пользователей должны остаться те же id**, иначе приложение «не увидит» свои локальные задачи.
- Участники поручений определяются **по email**, а не по id (`invited_emails`, `statusBy`, `report.by`, присутствие) — на сервере нужны оба.

## 6. Что из этого следует для нового сервера
- Сервер не должен ставить своё время правки: «кто новее» решает `updatedAt` с устройства. Списки отдаются целиком (у Supabase предел 1000 строк, клиент страниц не листает). Права теперь только на сервере: сейчас удаление и чтение идут лишь по `id`, а строка состояния имеет одинаковый id у всех — `access.py` обязан всегда добавлять «и это мой пользователь». Создание поручения с уже существующим id сервер должен отклонять.
- `sw.js` сейчас кладёт в кэш **все** GET-ответы, включая ответы облака с данными и фото. Для нового сервера запросы к API надо исключить из кэша.
- Тест `tools/test-buttons.js` подменяет именно адреса Supabase — на этапе 2 его заглушку надо переписать под новый API.
- `sync.js` можно сохранить по форме: те же функции `DaySync.*`, тот же алгоритм «лёгкий список → дозагрузка изменённого → запись». Сервер даёт 3 простых адреса на таблицу вместо языка запросов Supabase.
- Поручения: сервер получает **весь** `payload` целиком, поэтому `access.py` должен сравнить старую и новую версию поле за полем. Предлагаю белый список для исполнителя: `status` (кроме `completed`), `statusBy`, `statusAt`, `subtasks[].done/doneBy/doneAt`, `reports` (добавлять; удалять — только автор отчёта или организатор, как сейчас в экранах), `activity` (только добавление), `updatedAt`. Всё остальное — только организатор.
- Личные фото (задачи, чеки, фото профиля) сейчас лежат **внутри данных в виде текста base64**, а не файлами. В Supabase это раздувает трафик; на своём сервере трафик не ограничен, поэтому на этапе 2 предлагаю оставить как есть, а в файлы переносить отдельным шагом.

## 7. Расхождения ТЗ и работающего кода (правило 6 — нужен твой ответ)
1. **Совместные задачи и их фото/голосовые хранятся только в облаке.** На устройствах их нет, поэтому этап 5 «данные с устройства загружаются сами» их **не перенесёт**. *Предлагаю по умолчанию:* при первом входе на новый сервер устройство организатора само скачивает свои поручения и файлы из Supabase (у него есть права) и заливает на новый сервер.
2. **Пароли.** Supabase хранит пароли в формате bcrypt, а в стандартной библиотеке Python bcrypt нет. *По умолчанию:* пользователей всего 5 — админ (ты) задаёт им новые пароли через сброс админом, ID и email сохраняются. Альтернатива — 5-я библиотека `bcrypt`, тогда старые пароли подойдут.
3. **Push отложен**, но сейчас на нём держатся напоминания при закрытом приложении и кнопка «Напомнить» исполнителю. Без push они сработают только при открытом приложении. Это заметная потеря для монтажников. *По умолчанию:* как в ТЗ, push отложить; но подумай, не вернуть ли его сразу на этапе 3.
4. **Регистрация.** Сейчас любой может зарегистрироваться сам (с письмом подтверждения). В ТЗ — приглашения и сброс админом, писем нет. Значит меняются экраны входа и `reset.html`. *По умолчанию:* регистрация только по приглашению админа, вход по email и паролю, «Забыли пароль?» → «Обратитесь к администратору».
5. **Деньги.** Личные финансы хранятся в рублях дробным числом, в ТЗ — копейки. *По умолчанию:* личные финансы не трогаем (экраны те же), в сверке этапа 5 пересчитываем `round(сумма × 100)`; CRM сразу в копейках.
6. **Кто завершает поручение.** Кнопка статуса не даёт исполнителю поставить «Завершено», а галочка в списке дня (и свайп) — даёт. *По умолчанию:* завершает только организатор, галочка у исполнителя ставит «Готово, на проверке». Кнопки «выйти из задачи» сейчас нет — это новая кнопка на этапе 3.

7. **Данные на устройстве привязаны к адресу сайта** (так устроены браузеры). Если приложение переедет с `sharinskiy888-art.github.io` на адрес ПК или VPS, телефон не увидит задачи, сохранённые на старом адресе, и этап 5 «загрузятся сами» не сработает. *По умолчанию:* до переключения сайт остаётся на старом адресе, а `sync.js` просто начинает слать данные на новый сервер (нужен HTTPS — страница с https не может обращаться к http-серверу в местной сети). Запасной путь — «Резервная копия» на старом адресе → «Восстановить» на новом.
8. **Форма обратной связи** уходит на сторонний `formsubmit.co`. *По умолчанию:* перевести на свой сервер (сообщения видит админ).
