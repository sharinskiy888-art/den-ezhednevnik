# API сервера «День» (этап 1, опись до кода)

Сервер: FastAPI + SQLite. Все адреса начинаются с `/api`. Ответы — JSON в UTF-8.
Эта опись — договор между `sync.js` и сервером; тесты в `server/tests/` проверяют именно её.
Маркеры тестов: `etap2` — приёмка этапа 2 (вход, личные данные, права, копии), `etap3` — этапа 3 (поручения, файлы).

## Общие правила
- **Вход:** заголовок `Authorization: Bearer <access_token>`. Без него, с плохим, просроченным или отозванным токеном — `401`.
- **Ошибка:** `{"message": "текст для человека", "code": "короткий_код"}`. `sync.js` показывает `message`.
  - `400` неверные данные (в том числе кривой JSON и неверные поля; FastAPI-шный `422` сервер переписывает в `400`),
    `401` нет входа, `403` нельзя (не та роль или поле, которое вам менять нельзя),
    `404` нет такой записи **или она чужая** (чужие записи не «светятся»), `409` уже существует,
    `413` слишком большой запрос (сервер может и просто закрыть соединение, не дочитав тело),
    `429` слишком много попыток (+ заголовок `Retry-After` в секундах).
  - Тексты ошибок без подробностей устройства сервера (никаких трассировок).
- **Успех:** `200` с телом, `201` при создании (с телом), `204` без тела. Точные коды — в таблицах ниже.
- **Время правки** (`updated_at`) ставит устройство, сервер хранит его как пришло, строкой ISO 8601. «Кто новее» решает устройство (как сейчас).
- **Списки отдаются целиком**, без предела в 1000 строк.
- **`payload`** — непрозрачный JSON: сервер хранит его без изменений, неизвестные поля не трогает. `NaN` и `Infinity` — `400` (браузер такой JSON не прочитает).
- **Размер:** одна запись до 8 МБ, один запрос до 32 МБ, файл до 20 МБ. Считаются реально прочитанные байты, а не заголовок `Content-Length`.
- **Кэш:** все ответы `/api/*` с `Cache-Control: no-store` (иначе `sw.js` закэширует данные).
- **CORS** (разрешение браузеру обращаться к серверу с другого адреса): только адреса из `DEN_ALLOWED_ORIGINS`.
  Разрешены заголовки `Authorization`, `Content-Type`, `apikey`, методы `GET, POST, PUT, PATCH, DELETE`;
  `Access-Control-Expose-Headers: Retry-After`. Заголовок `Access-Control-Allow-Origin` есть и в ответах-ошибках (401, 413, 429), иначе браузер покажет «нет сети» вместо «войдите снова».
- **Журнал сервера** не содержит паролей, токенов, телефонов и адресов.
- **SQLite:** режим WAL, `busy_timeout` 5 с; одновременная запись с двух устройств не даёт ошибок.

## Хранение
- `den.db` — база. Таблица `users` со столбцом `password_hash` вида `scrypt$<параметры>$<соль>$<хэш>` (соль своя у каждого пароля).
- `files/shared/<task_id>/<имя>` — фото и голосовые отчётов.
- `backups/den-<время до миллисекунд>.db` — копии базы (через SQLite backup), рядом `files-<то же время>.zip` — копия папки `files/`, имена внутри архива — относительно `files/` (`shared/<task_id>/<имя>`). Имена не повторяются даже при двух копиях в одну секунду. Старые сверх `DEN_BACKUP_KEEP` удаляются.
- Второй сервер на ту же папку данных не запускается (файл-замок), чтобы два процесса не испортили базу.

## 1. Вход (`auth.py`)
Пароли — `hashlib.scrypt` с солью. Регистрации «с улицы» нет: только по приглашению админа.
Лимит: `DEN_LOGIN_LIMIT` неудачных попыток входа или регистрации за `DEN_LOGIN_WINDOW` с одного адреса **и** на один email → `429`; после окна снова можно.

| Метод и адрес | Тело | Ответ |
|---|---|---|
| `POST /api/auth/login` | `{email, password}` | `200` **Сессия**; неверный email или пароль — `401` с одинаковым текстом |
| `POST /api/auth/refresh` | `{refresh_token}` | `200` новая Сессия (полная, с `user`). Срок сессии (`DEN_REFRESH_TTL`) при каждом обновлении продлевается: пока человек пользуется приложением, его не выкидывает. Старый `refresh_token` ещё `DEN_REFRESH_GRACE` секунд принимается (выдаётся новая Сессия той же сессии); **повтор позже** — признак кражи: отзывается вся сессия (и новые токены тоже). Плохой — `401` |
| `POST /api/auth/logout` | — | `204`; эта сессия отзывается (и access, и refresh) |
| `GET /api/auth/user` | — | `200 {id, email, role}` |
| `PUT /api/auth/user` | `{password, old_password}` | `200 {id, email, role}`; неверный старый пароль — `403`. Все **прочие** сессии отзываются, текущая остаётся |
| `POST /api/auth/register` | `{email, password, invite}` | `200` Сессия; приглашение одноразовое и только для своего email, иначе `403` |

**Сессия:** `{access_token, refresh_token, token_type: "bearer", expires_in, expires_at, user: {id, email, role}}`;
`expires_at` — секунды с 1970 года, равно `exp` в токене.
**Токен:** `den1.<данные base64url>.<подпись HMAC-SHA256>`, в данных `{sub, email, role, iss, exp, sid}`; `exp` округляется вверх.
`sync.js` по началу `den1.` отличает вход своего сервера от старого входа Supabase и просит войти заново.
Отзыв работает через `sid` (номер сессии): отозванная сессия даёт `401` и для ещё «живого» access-токена.

Email всегда приводится к нижнему регистру и обрезается по краям. Пароль — от 8 символов (как требует окно входа), иначе `400`.

### Админ (`role = "admin"`)
| Метод и адрес | Тело | Ответ |
|---|---|---|
| `GET /api/admin/users` | — | `200 [{id, email, role, created_at}]` (без хэшей) |
| `POST /api/admin/users` | `{email, password, role?, id?}` | `201 {id, email, role}`; `id` можно задать (перенос пользователей из Supabase с теми же id). Занятый email или id — `409` |
| `PUT /api/admin/users/{id}/password` | `{password}` | `204`; все сессии пользователя отзываются («сброс пароля админом») |
| `DELETE /api/admin/users/{id}` | — | `204`; удаляет пользователя, его сессии и личные данные |
| `POST /api/admin/invites` | `{email, role?}` | `201 {invite, email, expires_at}` (живёт 7 дней) |
| `POST /api/admin/backup` | — | `201 {file, size}` — копия базы прямо сейчас, `file` — имя в `backups/` |
| `GET /api/admin/feedback` | — | `200 [{id, text, email, photo, created_at}]` |

Не-админ на любой `/api/admin/*` — `403`.

## 2. Личные данные (`sync.py`)
`{table}` — `tasks` (было `planner_tasks`) или `expenses` (было `planner_expenses`); любое другое — `404`.
Строки видны только владельцу; владелец всегда берётся из токена. Поле `user_id` в теле строки допускается (его шлёт нынешний `sync.js`) и игнорируется.

| Метод и адрес | Тело | Ответ |
|---|---|---|
| `GET /api/data/{table}/heads` | — | `200 [{id, updated_at, pu}]`, `pu` = `payload.updatedAt` или `null` |
| `GET /api/data/{table}` | — | `200 [{id, payload, updated_at}]` — все свои строки |
| `GET /api/data/{table}?ids=a,b,c` | — | `200` только эти (свои) строки; чужие и несуществующие молча пропускаются |
| `POST /api/data/{table}` | `[{id, payload, updated_at, user_id?}]` | `204`; вставка или замена своих строк. Одна плохая строка — `400`, и не пишется ничего |
| `DELETE /api/data/{table}/{id}` | — | `204`; свою строку. Чужую/несуществующую — тоже `204`, но ничего не происходит |

`id` — строка 1–100 символов, `payload` — объект, `updated_at` — строка. Особая строка «состояние приложения»
(`id = 00000000-0000-4000-8000-000000000001`) хранится у каждого пользователя своя.

## 3. Поручения (`shared.py`, этап 3)
Участник = организатор (`owner_id`) или email в `invited_emails` / `accepted_emails` (email без учёта регистра).
Строка: `{id, owner_id, owner_email, invited_emails, accepted_emails, leave_requests, payload, updated_at}`.

| Метод и адрес | Кто | Ответ |
|---|---|---|
| `GET /api/shared/heads` | участник | `200 [{id, updated_at, pu, invited_emails, accepted_emails, leave_requests}]`, по `updated_at` от новых к старым |
| `GET /api/shared?ids=…` | участник | `200` полные строки; чужие пропускаются |
| `GET /api/shared/{id}` | участник | `200` строка; не участник — `404` |
| `POST /api/shared` | любой | `201` строка. Организатор — из токена. `accepted_emails` и `leave_requests` при создании пустые, `updated_at` — как прислали. Свой существующий `id` — повтор: `200`, обновление как PATCH организатора. Чужой `id` — `409` |
| `PATCH /api/shared/{id}` | организатор | `204`. Меняет всё, кроме: `owner_id`/`owner_email` — только прежние; в `accepted_emails` можно только убирать (принимает сам приглашённый); иначе `403` |
| `PATCH /api/shared/{id}` | приглашённый, но не принявший | `403` |
| `PATCH /api/shared/{id}` с `base_rev` | организатор или исполнитель | Каждая строка поручения в ответах GET содержит `rev` — версию строки (меняется при любой правке, в том числе «Принять» и просьбе выйти). Если в теле PATCH есть `base_rev` и он не совпадает с текущей версией — `409 conflict`, ничего не меняется: приложение берёт свежую строку и повторяет действие. Поле `rev` в теле игнорируется. Отчёт удалили — его фото/голос удаляются с диска. Почта организатора из `invited_emails` убирается, адрес без `@` — `400`; новый `id` отчёта — только `[A-Za-z0-9_-]` |
| `PATCH /api/shared/{id}` | исполнитель (принял) | `204`. Только `{payload, updated_at}` (+ прочие столбцы, если они не изменились), и в `payload` — только поля из списка ниже, иначе `403` и ничего не меняется |
| `DELETE /api/shared/{id}` | организатор | `204`, вместе с файлами. Остальные — `404` |
| `POST /api/shared/{id}/answer` | приглашённый | `{accept: true}` → `204`, email переносится в `accepted_emails`; повтор — тоже `204`. `{accept: false}` — `400` (отказаться нельзя). Не приглашённый — `404` |
| `POST /api/shared/{id}/leave` | исполнитель (принял) | `204`: email попадает в `leave_requests`. Выйдет, когда организатор уберёт его из участников. Приглашённый, но не принявший, и организатор — `403`, посторонний — `404` |

**Что может менять исполнитель в `payload`** (всё остальное должно остаться как было):
- `status` — любое значение, **кроме** `completed`; `statusBy`, `statusAt`;
- `completed` — только `false`;
- `subtasks` — тот же список и те же названия, меняются только `done`, `doneBy`, `doneAt`; отметка ставится только от своего имени (`doneBy` = свой email);
- `reports` — не больше 50 (или прежнего числа); фото/голос нового отчёта — только `shared/<эта задача>/<имя>.<ext>`; новый список = старый без своих удалённых отчётов, с отрезанной головой (если всего больше 50 — `app.js` хранит последние 50) + свои новые (`by` = свой email) в конце. Чужие отчёты в середине не трогать;
- `activity` — новый список = хвост старого + свои новые записи (`email` = свой) в конце;
- `updatedAt`.
Не может: текст, дату, заметку, вложения, `nudgeAt`/`nudgeNumber`/`inviteReminder*`, новые поля, участников, владельца.

Удаление аккаунта убирает его почту из всех поручений: новый аккаунт на ту же почту чужих задач не получает.

## 9. CRM — клиенты, объекты, заявки, ТО (`crm.py`, этап 4)
**Роли CRM** (столбец `users.crm_role`): `manager` — всё; `worker` (монтажник) — только читает назначенные ему заявки, их объекты и клиентов этих объектов, и справочник; пусто — раздела нет (`403`). Админ всегда `manager`.
Назначает админ: `PUT /api/admin/users/{id}/crm {role: "manager"|"worker"|""}` или `python -m server.admin crm <email> manager|worker|none`.

| Метод и адрес | Кто | Ответ |
|---|---|---|
| `GET /api/crm/me` | любой вошедший | `200 {role}` (`""` — раздела нет) |
| `GET /api/crm/{kind}/heads` | manager, worker | `200 [{id, updated_at, pu}]` — только видимые этой роли |
| `GET /api/crm/{kind}?ids=…` | manager, worker | `200 [{id, payload, updated_at}]`; невидимые пропускаются |
| `POST /api/crm/{kind}` | manager | `204`. Тело — список `{id, payload, updated_at}`, как у личных данных. Надгробие — `payload: {id, __deleted: true, updatedAt}` |
| `DELETE /api/crm/{kind}/{id}` | manager | `204` (убрать истёкшее надгробие) |
| `POST /api/crm/maintenance` | manager | `200 {created}` — создать заявки ТО по договорам сейчас (сервер делает это сам каждые 10 минут) |
| `POST /api/files/crm/{object_id}?ext=jpg` | manager | `201 {path: "crm/<object_id>/<uuid>.jpg"}` — фото объекта |
| `GET /api/files/crm/{object_id}/{name}` | кто видит объект | `200` файл; иначе `404` |

`kind`: `clients, objects, orders, contracts, payments, dict`. Монтажнику `contracts` и `payments` — пустые списки. `id` — буквы, цифры, `-`, `_`, до 90 символов.

**Поля (`payload`).** Неизвестные поля хранятся как есть; известные проверяются (`400`):
- `clients`: `name` (обязательно), `inn` — строкой, `phone`, `email`, `contact`, `note`.
- `objects`: `clientId` (обязательно), `address`, `systems` — список строк из справочника, `equipment`, `note`, `photos` — список путей `crm/<id объекта>/…`.
- `orders`: `objectId` (обязательно), `type` (из справочника), `stage` — `new → kp → work → done → paid`, `assignees` — список email, `due` — `ГГГГ-ММ-ДД`, `sumKop` — целое ≥ 0 (копейки), `note`, `contractId`.
- `contracts`: `objectId`, `periodMonths` 1–24 (по умолчанию 1), `priceKop`, `nextDate`, `assignees`, `active`, `type` (по умолчанию «ТО»).
- `payments`: `orderId`, `kind` — `income|expense`, `amountKop` — целое > 0, `date`, `note`.
- `dict` (одна строка `id = "dict"`): `workTypes`, `systems` — списки строк. Пустой справочник: виды работ «Монтаж, Ремонт, ТО, Проект», системы «АПС, СОУЭ, Видеонаблюдение, Электрика».

**Заявка с исполнителями = поручение.** При записи заявки с непустым `assignees` сервер создаёт или обновляет поручение `id = "crm-<id заявки>"`: организатор — кто записал заявку, приглашены исполнители, название «<вид работ>: <адрес>», дата = `due`, `crmOrderId`. Статусы, отчёты с фото и голосовыми, напоминания — как у любого поручения. Исполнитель убран из заявки — убирается и из поручения. Заявка удалена — поручение удаляется вместе с файлами.

**Договор ТО.** Для активного договора, у которого `nextDate` наступит в ближайшие 7 дней, сервер создаёт заявку `id = "to-<id договора>-<дата>"` (вид «ТО», этап «new», `due = nextDate`, `sumKop = priceKop`, исполнители договора — значит, и поручение) и переносит `nextDate` на `periodMonths` вперёд. Повторный запуск ничего не дублирует.

**Скорость:** поиск и открытие карточки — на устройстве, без ожидания сервера (данные CRM синхронизируются на устройство так же, как задачи). Цель: поиск по любому слову среди 10 000 записей < 100 мс.

## 10. Перенос из Supabase и сверка (`migration.py`, этап 5)
**Как переезжает человек.** На телефоне остаётся вход прежнего облака (`localStorage day-cloud-old-v1`: id, email, токены Supabase). После первого входа на свой сервер **тем же email**:
1. Если у человека на сервере другой id, ключи телефона `…:<прежний id>` копируются под новый (кроме PIN — его задают заново). Чтобы обойтись без этого, админ заводит людей с прежним id: `python -m server.admin add <email> <пароль> --id <id из Supabase>`.
2. Обычная синхронизация загружает всё с телефона. Записи `planner_tasks`/`planner_expenses` из Supabase сливаются по правилу «новее побеждает» — более новая версия с телефона не затирается.
3. Поручения, где человек организатор, переносятся `POST /api/migration/shared`; исполнители становятся приглашёнными и принимают задачу заново (сервер не может проверить, что они принимали её в Supabase). Фото и голосовые отчётов — `PUT /api/files/shared/<задача>/<имя>` с прежними именами. Уже перенесённые задачи и файлы телефон запоминает и повторно из Supabase не скачивает; задача с постоянной ошибкой пропускается. При недоступном Supabase повтор через 2, 4, 8… минут, после 6 неудач — итог с ошибкой.
4. Итог уходит на сервер вместе со сверкой; вход Supabase стирается с телефона. Если вход Supabase истёк навсегда — перенос поручений пропускается, ошибка видна в сверке.
Другой человек, вошедший на этом телефоне, чужие данные не получает (сравнивается email).

| Метод и адрес | Кто | Ответ |
|---|---|---|
| `POST /api/migration/shared` | организатор | `201 {imported: true}`; уже переносилось (даже если потом удалено) — `200 {imported: false}`, ничего не меняется; чужой id — `409`; `DEN_MIGRATION` не `1` — `403 migration_closed`. Тело `{id, invited_emails, accepted_emails, payload, updated_at}`: все становятся приглашёнными; служебные поля из `payload` убираются |
| `POST /api/migration/report` | любой вошедший | `200 {ok, server, device}`. Тело `{device, label, counts: {tasks, plans, expenses, incomeKop, expenseKop}, supabase?}`; копейки — строкой |
| `GET /api/admin/reconcile` | админ | `200 [{email, status: "совпадает"\|"расхождение"\|"нет отчёта", server, devices}]` |

**Копейки** считаются одинаково на телефоне и сервере: по десятичной записи числа с округлением половины вверх (19,995 ₽ = 2000 коп.; простое `×100` в JS дало бы 1999).
**Окно переноса:** на время переезда в `den.env` пишется `DEN_MIGRATION=1`, после — убирается. Сверка хранит до 20 устройств на человека.
Сверка повторяется после каждой синхронизации, если числа изменились: `python -m server.admin reconcile` показывает итог по каждому человеку и устройству.

## 11. Модуль АК-Сервера (`ak.py`, код `crm`)
Та же программа. Если ядро передало `AK_MODULE_SECRET`, сервер работает модулем: `den.env` не читается, данные — в `AK_DATA_DIR`, слушает только `AK_HOST:AK_PORT` (127.0.0.1; другой адрес — отказ запуска).

**Каждый запрос** (кроме `GET /m/crm/healthz`) проверяет `ak.Gate`: строка `v1|core|crm|METHOD|PATH?QUERY|sha256(тело)|X-AK-Time|X-AK-Nonce|X-AK-User|X-AK-Org|X-AK-Roles|X-AK-User-Name`, HMAC-SHA256 ключом `bytes.fromhex(AK_MODULE_SECRET)`, время ±60 с (секунды Unix или RFC3339), nonce (16–128 символов) не повторяется 120 с. Не прошло — `401 bad_sign | replay`. Затем срезается `AK_BASE_PATH`: дальше те же адреса `/api/…` и экраны. Вне `/m/crm/` — 404, `/m/crm` → `308 /m/crm/`.

**Кто вошёл** — `X-AK-User` (UUID). Без него открыты только `/healthz` и `/ak/v1/*`; служебные `/ak/v1/*` с пользователем или с признаками браузера (`Cookie`, `Origin`, `Sec-Fetch-*`) — 404. Роли (`access.ak_crm_role`): owner, admin → руководитель CRM; только viewer → просмотр всего без правок; любая другая → монтажник; без ролей — CRM закрыта. Администратор «Дня» — owner. Ключ человека в поручениях и заявках — `<uuid>@ak` (email ядра не используется: его могут сменить или отдать другому); имена — из `employees` и из `X-AK-User-Name` (`unquote_plus`, хранится в `users.name`). Ядро нужно только для списка сотрудников; не отвечает — список из тех, кто уже входил (`503 core_unavailable`, только если никого нет).
Заголовок `X-Den-User` от приложения сверяется с `X-AK-User`: не совпал (в ядро вошёл другой) — `409 user_changed`, приложение переключает данные.
Заголовок `X-Den-Epoch` — метка данных вкладки; не совпала с `meta.epoch` (владелец восстановил копию) — `409 data_restored`, приложение забывает данные на устройстве и перезагружается. Пока идёт восстановление, запросы сотрудников — `503 restoring` (приложение повторит через 4 с).
Выключено: `/api/auth/*`, `/api/admin/users*`, приглашения, `PUT /api/admin/users/{id}/crm` (`403 ak_mode`), свои ежедневные копии.

| Метод и адрес | Кто | Ответ |
|---|---|---|
| `GET /m/crm/healthz` | без подписи | `200 {ok, version: "1.0.N", app: "N"}`; после команды stop — 503 |
| `GET /m/crm/api/ak/me` | сотрудник | `200 {ak: true, user: {id, email, name, role}, crm_role, epoch}` |
| `GET /m/crm/api/ak/employees` | сотрудник | `200 [{id, name, key}]` — справочник `employees` ядра по курсору (до `more:false`), кэш 60 с, без `deleted:true`, плюс все, кто уже входил |
| `POST /m/crm/api/ak/restore` | только owner | тело — zip (до 100 МБ): архив АК `ak-….zip` или свой zip копии → `200 {ok, copy, rows, aside, epoch}`; плохой архив — `400 bad_backup` (данные не тронуты); не owner — 403 |
| `GET /api/ak/me` (отдельный сервер) | все | `200 {ak: false}` — приложение показывает свой вход |
| `GET /m/crm/ak/v1/busy` | ядро | `{busy, reason}` — занят, пока идёт копия, восстановление или запрос сотрудника |
| `POST /m/crm/ak/v1/stop` | ядро | `200`, затем штатное завершение (база сброшена в основной файл) |
| `POST /m/crm/ak/v1/backup` | ядро | `{name}` (`ГГГГ-ММ-ДД_ЧЧММ`) → `AK_DATA_DIR/.backup/<name>/den.db` (backup API) + `files/`; хранятся 3 последние |
| `POST /m/crm/ak/v1/events` | ядро | `{seq, event_id, type, source, time, data}` → `200 {ok, duplicate}`; повтор `event_id` не обрабатывается; без `event_id` — `200 {ok, ignored}` (очередь ядра не встаёт) |

**Клиенты ↔ справочник ядра `partners`** (`partners.py`). Главный список клиентов — у ядра, в базе модуля — рабочая копия (`crm`, `kind='clients'`), поэтому «Клиенты» работают и без ядра. Сохранение клиента (`PUT /api/crm/clients`) в той же транзакции ставит строку в очередь `core_outbox`; фоновый поток раз в 2 с шлёт `PUT /core/v1/partners/{id}` полной записью `{rev, name, inn, phone, email, contact, note[, deleted:true]}` (удаление — только `deleted:true`). `409` — взять запись ядра, запомнить её `rev` (`core_links`) и отправить ещё раз; `400` — строка остаётся, в журнал (только id и код) и `POST /core/v1/notify` владельцу, повтор через час; нет связи, 5xx, 401 — повтор через 10 с, 1 мин, 5 мин, 30 мин, дальше раз в час. Событие `partner.changed {id, rev}` — если rev новее известного, `GET /core/v1/partners/{id}` и замена копии (своя неотправленная правка важнее). При запуске, после сбоя связи и раз в 10 минут — полный проход `GET /core/v1/partners?cursor=…&limit=500`: чужие изменения — к себе, свои клиенты, которых в ядре нет или у ядра rev меньше нашего (ядро восстановили из копии), — в очередь.

**Перенос прежней установки** (`legacy.py`). При первом запуске модуля (базы в `AK_DATA_DIR` ещё нет) берётся самая свежая из `C:\Users\*\AppData\Local\Den\data` и `C:\ProgramData\Den\data`: копия `den.db` (+ `-wal`) во временную папку модуля → backup API → `quick_check` → без прежних входов (`sessions`) → `files/`; прежняя папка только читается. Люди прежней установки переходят к сотрудникам ядра при первом входе: по совпадению email с логином или email сотрудника в ядре (`/core/v1/users/{uuid}`, справочник `employees`), владельцу — данные единственного прежнего администратора.

Запросы к ядру (`ak.core`): подпись с FROM=`crm`, TO=`core`, заголовки `X-AK-From/Time/Nonce/Sign` (+ `X-AK-User`). Пакет: `bash deploy/ak/build_module.sh` (на Linux, свой Python 3.12 для Windows и `crm.cmd`) или `python deploy/ak/make_module.py <сборка> <папка>` → `AK-Crm-Modul-1.0.N.zip`; проверка как у ядра — `deploy/ak/smoke.py`. Заглушка ядра для тестов и ручной проверки — `server/tests/ak_core.py`.
